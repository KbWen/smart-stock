## Global Lessons (AI Error Pattern Registry)
>
> 3-5 high-value patterns max. Reviewed during /bootstrap.

- [Build Mode Strictness]: `tsc --noEmit` may pass while `npm run build` (`tsc -b`) fails on stricter generic type constraints (e.g., Recharts Formatter). Always run full production build as final validation before shipping.
- [Format Safety]: Do not copy line numbers from view tools; they break file edits.
- [E2E Perf Testing]: E2E performance tests must run against production build (`vite preview`), not dev server. React StrictMode double-invocation in dev inflates timing 3-6×, masking true render performance.
- [Work Log Lag]: Evidence must be written to Work Log during each phase (implement/review/test), not accumulated for ship. Stale logs block the ship gate and require recovery before proceeding.
- [Rotation Conflict]: When trainer.py uses timestamp-based rotation and manage_models.py uses quality-based pruning independently, a bad new model can displace a good old one before prune runs. Unify via a shared constant and quality-first sort key.
- [Sidecar Parity]: Whenever a `.pkl` model file is deleted (rotation or prune), also delete matching `.sha256`/`.sig` sidecars. trainer.py rotation and manage_models.py:cmd_delete must stay in sync on this.
- [Stacked-PR Merge]: When merging stacked PRs, retarget each dependent PR's base to mainline BEFORE merging+deleting its base branch. `gh pr merge --delete-branch` on the base auto-CLOSES the dependent PR and GitHub will NOT reopen it once the base branch is gone (cost a #23→#25 recreation). Either retarget-first, or omit `--delete-branch` until dependents are retargeted.
- [Claim vs Real Target]: Verify "it works" against the REAL target scenario, not the local dev state. The onboarding "populated dashboard" claim was false for a fresh clone (gitignored storage.db/model) until a recalc model-gating bug was fixed — local dev had a model so it masked the gap.

### Ship-feature-unknown-is-not-zero-ml-features-2026-09-02
- Feature shipped: **Unknown Is Not Zero epic #1**, opened from a triage of the 12 GitHub issues untouched since 2026-06-05 (GH #14). A feature the model needs but the history cannot support was filled with `0` — which is not a blank: `dist_sma240 = 0` asserts *the price sits exactly on its 240-day mean* and a slope of `0` asserts *flat*, both among the most ordinary states a stock can be in, which is why nothing downstream could tell anything was missing. Measured on ticker 2330's real last trading day, holding the day fixed and varying only supplied history: full history `dist_sma240 = +0.3429` (34.3% above its annual mean, a pronounced uptrend), 150 rows `0.0` (exactly on it). `predict_prob` now returns `None` when any `FEATURE_COLS` value on the prediction row is not finite — its existing failure contract, so `ai_prob` is `NULL` and the UI shows N/A **with a reason**. The requirement, **250 rows** = the 240-period SMA plus its 10-row slope, was already in the codebase as `MIN_TRAIN_ROWS`' rationale; training used it, inference never did. **Training was never affected** — `trainer.py` drops warm-up rows before the fill, with a comment naming this exact hazard; that line was load-bearing, untested, and is now pinned. Three quieter substitutions went with it: the prediction path no longer forward-fills yesterday's indicator into today's row; a model asking for a column the frame lacks is no longer handed it as `0` via `reindex(fill_value=0)`; and the two request paths that zero-fill the frame for the JSON payload now give the model the **unfilled** frame — without which **the whole feature would have been inert on two of three request paths while every unit test passed**, because with `sma_240 = 0` the finite check sees an astronomical number rather than a NaN, and unit tests build raw OHLCV where the NaN is real. **Both reviewers returned NOT READY on disjoint briefs and converged on the same HIGH**: a 250-row cliff dropped into a codebase whose loaders size their windows in **calendar** days. `RECALC_LOOKBACK_DAYS = 420` yields ~225 trading rows on the shipped panel, so **91 of 92 tickers refused** — the first nightly recalculation would have wiped the AI probability product-wide, with `INSERT OR REPLACE` writing those NULLs over good values the 730-day sync path had just produced. **My CHANGELOG said this was impossible: I had measured rows in the table, not the window each caller loads.** Raised to 730; measured after: 0 of 92, pinned by a test against `MIN_FEATURE_ROWS`. Second HIGH, also from both: `backend/backtest.py` coerced the refusal with `ai_prob = ... or 0.0` and dropped the pick through the **strategy filter** — a refusal booked as "the model said 0%", this epic's defect one layer down in the module producing the headline numbers; it now has an `excluded_unscorable` bucket and the counts survive the no-picks branch, which discarded all three. ### Ship-feature-rotation-ranking-honesty-2026-09-02
- Feature shipped: **Honest Metrics epic #4 — the epic's last P0, and the only item in it whose failure mode is irreversible.** Rotation and `manage_models prune` `os.remove` `.pkl` files ranked by `backtest_30d.profit_factor`, which carried no marker for how it was measured. Before #1 a winning trade was booked at the session **high**; after #1 both sides settle at achievable fills, which on the same seed and window moved profit factor **0.74 → 0.80** — so **a genuinely better old model could be deleted for having been measured with a different ruler**, and the file does not come back. A fourth defect the quant panel had not named surfaced while reading the code: `profit_factor: None` meant **both** "no losing trades" (a flawless run, from `backtest.py`) and "the benchmark raised" (from the trainer), and the `-1.0` sort key ranked both *below* a model that lost money on every trade. The rule now: **an irreversible action requires a comparable measurement.** `select_for_deletion` ranks only entries matching on `(settlement, days_ago, holding_days)` with a finite profit factor; everything else is **protected**, not sorted last — the store may exceed `MAX_SAVED_MODELS`, which is logged with the manual prune command. **The reviews changed the shape of the fix twice.** The pre-mortem found the first implementation's protection **expired silently at ~50 entries**: deletion globbed every `.pkl` and removed anything not in a keep-set built from a history truncated to 50, so a nightly retrainer would have lost the oldest protected file around night 52 with no check and no log line — deletion is now an **allow-list**. And both reviewers independently derived that **AC5 asserted a property no window can deliver**: the final ensemble is refit on every row and training labels resolve through T, so any window ending before T is inside the training data and raising `days_ago` buries it *deeper*. The window went back to 30 and the entry records `in_sample: true` — the claim was removed rather than reworded into something that sounds delivered. ### Ship-feature-date-based-embargo-2026-09-02
- Feature shipped: **Honest Metrics epic #2** — the training embargo was measured in **pooled rows** on a cross-sectionally stacked panel. One date contributes N rows, so `X_all.iloc[:split_idx - PRED_DAYS]` removed `PRED_DAYS/N` days. The audit estimated ≈0.2 trading days at 92 tickers; **measured on the real panel it was 0** — train and test shared a boundary date, so the model was scored on outcomes it had trained on. `TimeSeriesSplit(gap=PRED_DAYS)` had the same defect (sklearn's `gap` is in samples). **Root cause**: an embargo is a statement about *time*, implemented as row arithmetic; the two are equivalent only when N=1, which is the shape the code was written against — correct when written, silently wrong the moment a second ticker was added. Replaced by a pure `chronological_split(df_all, pred_days)` that walks the panel's **own sorted unique dates**, with the CV gap scaled by `max_rows_per_date` (the max, not the mean, being the only choice that guarantees ≥ `PRED_DAYS` distinct dates on an uneven panel). Extracted as a function so the invariant is directly testable and so the trainer and `scripts/eval_label_modes.py` cannot drift. **Measured effect** (one process, one panel, one seed, both splits): StrongBuy recall **0.744 → 0.629**, precision 0.352 → 0.345, training rows −3.2%. **The pre-mortem caught a regression this change introduced**: treating an infeasible CV gap as fatal put a cliff under the product at ~`4 × PRED_DAYS` distinct *training dates*, **independent of ticker count**, which the shipped demo fixture would have crossed as its rolling window slid — silently leaving fresh clones unable to train. Fixed by design, not threshold: the CV loop is **diagnostic only** (each fold's model is fit, printed, discarded), so it degrades 3→2→skipped while the holdout embargo still aborts when it cannot be honoured — new `[DECISION]`: *degrade diagnostics, never the guarantee*. Also fixed from review: `setup_real_ai.py` reported `trained: True` unconditionally; `train_and_save` now returns `bool` and `train_ai.py` exits non-zero; `history_entry` gains an `embargo` block so entries **lacking** it are a machine-readable pre-fix marker; NaT and tz-aware date guards; supersession pointers on the frozen `ai-pipeline-otc-optimization.md` AC3, two `DATA_INTEGRITY.md` rows, `REPRODUCE.md` and `troubleshooting.md`. **Honest disclosure carried into the ship note**: with a clean split StrongBuy precision `0.3454` sits **below** the test-split prevalence `0.3512` — no skill to negative skill — and `core/ai/predictor.py:195` will still call that model `ok`, so shipping #2 before #5 makes the health check most wrong exactly when the metrics are most honest.
